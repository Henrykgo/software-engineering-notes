Rag retrieves relevant information from external sources and puts it into the prompt so the model can base its answer on it rather then from its own weights. This is how a model can get knowledge it has not been trained on without fine-tuning.

An external source can be an internal database, a user's prevous chat sessions or the internet.

### Why RAG?
- Gives the model knowledge it was never trained on (private or recent data)
- having access to relevant information can help the model generate more detailed responses as well as reduce [[Hallucinations]]
- context windows are limited and models can use long context badly
- if model fails because of lack of information a rag system giving the model access to the relevant sources of information can help
### How it works?
2 Components: a retriever (retrieves information from external memory source) and a generator (the model that will generate the response based on the information retrieved)

##### Indexing (Once, ahead of time)
1. Split document into chunks (chunking strategies?)
2. Turn each chunk into a searchable form: term based or as a vector form a  [[Embeddings]] model.
3. Store them as a index ([[Vector Search]]). 

##### Querying (per request)
1. Turn the query into the same form using the same method (as used for the indexing)
2. Get the top-k closest chunks ([[Retrieval]])
3. Add them to the prompt and let the model answer.

#### Retrieval Optimisation
Ways to improve what the retriever returns

##### Chunking
- fixed length (characters, words, sentences, paragraphs)
- recursively: split by section and keep splitting until the desired length
- splitters for different programming languages
- creative ways e.g. Q/A pairs as chunks
- Overlap so chunk is not cut off in the middle of important context
- Tokens size (downside is that changing model will have to reindex)

Smaller or bigger chunk size?
- Smaller chunk size can fit more diverse info, fit more chunks into model context, provide model with wider range of info leading to better asnwers
- it also causes the loss of important info (e.g. splitting document with important info into on X into 2 halves but X is only mentioned in first half, the second have of document might not be retrieved so the model will not be able to use it)
- increase computation overhead (especially for embedding-based retrieval, as you have more embedding vectors to generate and store)
##### Reranking
- the initial document rankings generated by the retriever can be further reranked to be more accurate (using a cheaper retriever to fetch candidates and then using a more precise but expensive one to rerank these candidates)
##### Query rewriting
- rewrite queries to reflect what the user is actually asking. e.g. "has he bought something from us" should be rewritten to the persons name before retrieving anything
- usually done with a AI model
##### Context retrieval
- add metadata to each chunk before indexing: title, tags, summary or a sentence saying where the chunk sits in its document
- helps chunks that are meaningless on their own

#### RAG beyond text
- multimodal: retrieve images (audio/video etc) with a multimodal embedding model such as CLIP, so a text query can match a image
- tabular (text-to-SQL): the model writes a query, the database runs it and the model answers from the result
#### Compare with 
- finetuning: changes how the model behaves, not what it knows
- Long context: simpler but the cost and latency increases as prompt length increases and the model can struggle to find the relevant part
